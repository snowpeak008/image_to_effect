# 视觉迭代、证据与经验递归规则

版本：`1.0-draft`  
适用范围：所有 Archetype、所有人工与 AI 辅助特效生产

## 1. 强制迭代账本

每次视觉候选都必须记录以下内容，不论成功或失败：

1. 本轮冻结目标与禁止项；
2. 实际修改的模块、资源和 Runtime 行为；
3. Compile、EditMode、PlayMode、Player/性能等机器结果；
4. 同一 WYSIWYG 链路的证据路径；
5. 人工结论：`accepted / conditional / rejected`；
6. 失败时的直接现象、技术根因与设计根因；
7. 下一轮只允许修改的范围；
8. 新增的防回归测试或尚不能机器化的人工检查。

机器通过不得自动写成视觉通过。用户拒绝后，状态必须立即改为 `rejected`。

## 2. 证据生命周期

- 当前候选只能有一个 `current-run`。
- 新候选生成前，失败证据必须移动到带日期和原因的 `rejected-run-*`，禁止覆盖或删除后伪装首次成功。
- 成功证据可进入 `accepted-run-*` 或由报告固定唯一权威路径。
- Unity 活动资产目录只保留当前正式资源；历史截图和研究证据放在 `docs/`，不得堆入 Runtime 包。

## 3. 经验递归

出现过的错误必须从单个 Effect 复盘上升到全项目规则：

- 可自动检测的根因写成测试或机器门禁；
- 只能人工判断的视觉项写入关键帧清单；
- 架构性错误写入 ADR 或核心规则；
- 资源、Shader、混合、相机、生命周期与展示方式的经验写入 `60_ENGINEERING_LESSONS.md`；
- 后续相同类型开工前必须先读取相关经验，不得重复探索已知失败路径。

## 4. 修改闭环

标准循环为：`冻结目标 → 最小候选 → 工程验证 → 同链路抓帧 → 主动人工审查 → 用户审查 → 记录成功/失败 → 根因递归 → 下一候选`。

只有用户明确接受或计划中指定的决策人签署后，视觉阶段才能关闭。工程代理不得因为测试全绿自行跳过用户验收。
